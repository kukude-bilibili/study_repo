## Q1: 签名如何识别内容被修改？

签名本质是**加密哈希**。API 生成签名时，对 thinking 内容做了"指纹计算"：

```
发送时：  thinking = "我需要先读取文件..."  →  哈希 →  signature = "abc123"
存储后：  thinking = "我需要先读取文件..."  →  签名 = "abc123"  ✅ 匹配
篡改后：  thinking = "我决定直接删除文件"  →  签名 = "abc123"  ❌ 不匹配
```

API 收到请求时，重新对 thinking 做哈希，和签名对比。内容改了一个字，哈希就完全不同，签名直接失效。

**关键：mewcode 不需要做任何验证逻辑，API 自己算自己比。**

## Q2: 为什么拼接 JSON 再解析为 Map？

拼接是为了**完整性**，解析为 Map 是为了**可用性**。

```
流式传输（分片到达）：
  片段1: {"name"
  片段2: ": \"read"
  片段3: "_file\", \"pa
  片段4: "th\": \"/etc/ho
  片段5: "sts\"}"

拼接后：{"name": "read_file", "path": "/etc/hosts"}  ← 完整 JSON 字符串

解析为 Map：{name: "read_file", path: "/etc/hosts"}    ← 可以直接 .get("path")
```

- **拼接成字符串**：流式传输把一个 JSON 拆成了碎片，不拼起来没法用
- **解析为 Map**：保持字符串的话，每次要用参数都得手动解析 JSON，又慢又容易出错。Map 可以直接 `params.get("path")`，一行代码搞定

## Q3: 为什么不把 `stop_sequence` 放入 stopReason？

`stopReason` 是**原因**，`stop_sequence` 是**触发了什么**。分开存是两种不同的信息：

```java
// 分开存：
stopReason = "stop_sequence"    // 为什么停？因为遇到了停止词
stopSequence = "---END---"      // 遇到了哪个停止词？

// 如果合并：
stopReason = "stop_sequence:---END---"  // 混在一起，上层要解析字符串才能拿到两个信息
```

stopReason 还有其他值（`end_turn`、`max_tokens`、`tool_use`），只有 `stop_sequence` 这一种情况才需要附带具体是哪个停止词，分开存更清晰。

## Q4: 什么是系统级错误（java.lang.Error）？

区分两类：

| 类型 | 例子 | 含义 |
|------|------|------|
| **StreamEvent.Error**（业务错误） | API 返回 500、网络超时、token 用完 | "这次请求失败了，但程序还能继续跑" |
| **java.lang.Error**（系统级错误） | `OutOfMemoryError`、`StackOverflowError`、`NoClassDefFoundError` | "JVM 本身出问题了，程序基本活不下去了" |

**一句话：StreamEvent.Error = 可以恢复的意外；java.lang.Error = JVM 级别的致命伤，通常不应该 catch，让它崩。**
