#7-#10 费曼自问自答（录音用答案）
#7：ToolResult 为什么用 record 而不是普通 class？

Plain Text

三个原因：
1. 不可变性：record 所有字段默认 final，ToolResult 创建后不可修改。
   多线程并发执行工具时，多个线程读同一个 ToolResult 不会出现数据竞争。
2. 自动生成样板代码：equals/hashCode/toString/全参构造器由编译器自动生成，
   不需要手写，减少出错。ToolResult 作为纯数据载体，不需要自定义行为。
3. 语义清晰：看到 record 就知道这是一个"数据类"，不包含业务逻辑，
   阅读代码的人一眼就能理解它的职责边界。
#8：为什么 ToolResult 和 ToolResultBlock 要分开定义？

Plain Text

分层解耦原则：
1. ToolResult 属于 tool 包（工具执行层），只关心"工具执行后产生了什么结果"。
   它不应该知道 tool_use_id（那是 LLM 调用层面的概念），
   也不应该知道自己在对话历史中的位置。
2. ToolResultBlock 属于 conversation 包（对话层），它的职责是把工具结果
   与 LLM 的 tool_use 调用一一对应。tool_use_id 是对话层概念，属于这里。
3. 如果合并成一个类，ToolResult 就会同时依赖 tool 包和 conversation 包，
   形成循环依赖的风险。分开后，tool 包完全不依赖 conversation 包，依赖方向清晰。
4. ToolResultBlock 直接映射到 Anthropic/OpenAI API 的 tool_result 消息块格式，
   如果 ToolResult 混入 API 协议细节，每次 API 变化都要改工具层代码。
#9：ContextCompactor 为什么用两层压缩？

Plain Text

成本与质量的平衡：
1. Layer 1（本地裁剪）：零 API 成本。超过 15K 的单条结果写入磁盘并替换为路径引用，
   超过 20K 的聚合结果按大小降序溢出。这些操作只消耗 CPU，不消耗 LLM token。
2. Layer 2（LLM 摘要）：高质量压缩。当 token 超过 80% 阈值时才触发。
   用 LLM 生成结构化摘要（XML 格式），保留关键信息（文件路径、决策、待办）。
3. 关键设计——熔断器：Layer 2 连续失败 3 次后自动跳过，防止无限重试浪费 token。
4. 恢复机制：RecoveryState 在压缩时附加文件快照和 Skill SOP，
   确保模型不丢失关键细节。
#10：ToolResultBudget 的 Design B 好在哪？

Plain Text

Design A（旧方案）：ContextCompactor.offloadAndSnip 直接修改输入 ConversationManager。
问题：修改了原始输入，导致 Anthropic prompt-cache 的前缀不稳定。
缓存依赖于"前 N 条消息完全相同"，一旦修改了之前的消息，缓存全部失效，token 成本飙升。

Design B（新方案）：不可变输入 + 创建新 ConversationManager。
1. 原输入不动，创建新对象进行裁剪，返回 ApplyResult（新 ConversationManager + 替换记录）。
2. prompt-cache 稳定：因为原始输入不变，LLM 每次请求的前缀完全一致，缓存命中率高。
3. 无副作用：调用方传入的参数不会被修改，函数式编程风格，易于测试和推理。
4. 可回滚：保留原始数据，出现问题可以回退。
5. 用额外的内存开销换来了可预测的缓存行为和更低的 token 成本，这是值得的。
